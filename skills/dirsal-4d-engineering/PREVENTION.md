# 4D Engineering — Permanent Prevention and Verification

Apply SKILL.md, AUDIT_AND_REMEDIATION.md and all current global/workspace/module rules. This is a procedure for establishing effective safeguards, not an independent policy hierarchy. Never install or modify anything merely because it appears in this document. Phase 2 establishes minimal approved gates early; Phase 4 tightens them based on audit findings and verified architecture. Use actual project tooling and evidence.

## 1. Choose the minimum effective controls
Inventory current lint, type, build, test, security, graph, contract and CI tooling. Inspect scripts, subprocesses and hooks for Git commands, automatic service starts, external data upload, writes, environment changes and network effects. No agents may run Git directly or indirectly; never start/stop services. Check package-local dependencies, tool versions and native capabilities before proposing additions. Prefer existing tools and native language checks. Obtain explicit approval for installation, dependency/lockfile changes, external scanning, CI workflows and global configuration. Do not run unreviewed npx or install-on-demand commands. Existing CI can be used only according to operator authority and existing restrictions; don't introduce agent Git operations to obtain changed-file scope.

Candidate controls (not mandatory tools):
| Lens | Initial controls | Additional when justified |
|---|---|---|
| Drift | Existing lint/import rules; graph checks; allowed dependency direction and cycles; go vet, approved Go import checks, Flutter/Dart analyzer | dependency-cruiser, custom ESLint/Semgrep, ArchUnit/Import Linter, Nx rules only if applicable |
| Duplication | Scoped full-workspace clone scan, existing unused-code analysis, canonical contract/owner checks | jscpd, Knip, ast-grep, SonarQube; semantic findings reviewed with evidence |
| Degradation | Existing build/type/tests; native Go/TS/Dart checks; security/secret/dependency scans and invariant tests | Gitleaks, OSV-Scanner, govulncheck, Trivy, Semgrep, CodeQL, Stryker, property/concurrency tests, k6/Lighthouse where safe |
| Desynchronization | Existing schema/spec and generated artifacts checks; consumer integration; migration validation; localization keys/placeholders | oasdiff, Pact, AsyncAPI, Buf, GraphQL Inspector, Schemathesis, existing package/version tooling |

Use existing make sqlc / make genspec / pnpm generate:api or equivalent only where verified applicable and safe; generation can write files or require a running service. Prefer a read-only freshness check or safe temporary output comparison when possible; never silently regenerate during audit. Use operator-started authorized services if required. Existing service-less tests can be run within their approved constraints; inspect test runners that launch servers or containers automatically. If tooling cannot comply, mark blocked and provide operator steps.

## 2. Baseline-aware gates with repo-wide visibility
1. Define each check's scope, language/tool/version, config, exclusions, reproducible command, expected output, deterministic finding identity and owner. Analyze the whole applicable dependency/contract graph, not just edited lines. Cross-module clones/cycles and producer/consumer breaks can involve untouched files. For polyrepo work, coordinate full-workspace results; do not require all repos to share one build system. Use verified authorized non-Git file manifests/fingerprints to identify changed scope where necessary.
2. Capture original results and known failures from BASELINE.md. Distinguish historical debt from new/worsened problems using stable identities (rule + unit + path/symbol + normalized evidence or appropriate tool fingerprint); do not rely only on total counts, which can hide new findings after old ones disappear. Record rule/tool changes, renamed paths, ambiguous matches, scope changes and manual decisions. Do not auto-accept a regression because counts fell.
3. Establish blocking rules for verified new/worsened objective failures, or any existing failure already blocking under governing rules. Historical debt remains visible, prioritized and subject to risk-based remediation; do not waive critical vulnerabilities or secrets by default. Approved temporary exceptions have owner, scope, justification, compensating controls, approval and expiry; never suppress broad categories to get a green report. Approved baseline remains immutable; controlled ratchets require review, never reset to hide failure.
4. Run safe positive and negative fixtures: prove valid code passes and intentional isolated violations fail. Do not introduce violations into production files just to demonstrate a gate. Verify exit codes and failure propagation; report whether a check is merely documented, runnable locally, executed, or actually enforced by CI/operator workflow. No CI means no claim of CI enforcement. Document operator command and manual enforcement until approved CI exists.
5. Re-run applicable gates after each remediation batch. Track comparable metrics by module and globally. Require source anchors and evidence. Missing execution, unsupported tools and ambiguous findings are explicit blockers or review items, not pass results.

## 3. Rules by D — add only missing enforceable requirements
Compare actual AGENTS.md and applicable local instructions before proposing any new text. These statements describe desired safeguards, not text that must be duplicated verbatim into every project. Keep global policies in their existing authoritative location and product/domain specifics locally. Agent adapters (CLAUDE.md, Codex AGENTS.md, Cursor User Rules, Antigravity supported instructions, GEMINI.md only if applicable) should reference canonical instructions as supported; verify actual discovery and do not maintain duplicate independent policy copies. Obtain approval for global/project instruction edits. Never weaken HARD RULES or modify unrelated instructions. If the policy already exists, add only the missing verification procedure/control.

### Canonical global prevention rule (proposed exact policy, not a fourth skill file)
During Phase 2, compare the existing global policy and adapters; obtain explicit authorization for any missing or inconsistent text. Keep one canonical AGENTS_GLOBAL.md at the verified authoritative location. Do not assume a bare path reference is automatically loaded; verify supported imports/links or native User Rules and actual instruction discovery. If an agent requires a materialized copy, use an approved deterministic sync and hash verification, not independently maintained text. Preserve every unrelated HARD RULE. The following text is the approved design for the 4D policy; actual edits require separate approval and reconciliation with existing wording.

> ## HARD RULE — 4D Engineering Prevention
>
> All development tasks must prevent Drift (architecture and ownership deviations), Duplication (unnecessary repeated implementations), Degradation (quality, security, reliability, performance and business integrity loss), and Desynchronization (inconsistent consumers, contracts, schemas, configuration, tests and documentation).
>
> Before implementation, identify reusable functionality, affected modules, dependencies, authoritative sources and applicable business rules. Before completion, execute applicable automated 4D checks and resolve newly introduced violations. Use the dirsal-4d-engineering skill and PREVENTION.md for complex changes, cross-module work, refactoring, shared packages, architecture and critical business logic. Use AUDIT_AND_REMEDIATION.md to investigate or correct existing 4D violations. Never bypass 4D safeguards. Existing global, workspace and module HARD RULES remain binding. Report unavailable checks; do not claim verification that did not occur.

### Drift
Before implementation identify approved owner, architecture and dependency direction. Check existing patterns; avoid new frameworks/abstractions without demonstrated requirement and required approval. Respect private/public boundaries and server-side security. Material architecture decisions require approved existing ADR/MEMORY process, not a new governance file. Enforce objective prohibited imports, cycles, ownership boundaries and approved patterns using compatible checks. Do not enforce legitimate variation as drift.

### Duplication
Search the relevant codebase (graph first where required) and shared packages before creating functions, components, services, schemas, endpoints, hooks or business rules. Reuse first, extend when justified, create only when needed. Keep canonical domain authority in its owner; consume public contracts. Require evidence of consumer discovery, behavioral differences and justification for consolidation/new package. Detect exact/structural clones and unused-code candidates automatically; semantic duplicates require evidence and independent review where critical. Do not force shared packages or 0% duplication. Prohibit speculative abstractions and competing authoritative implementations. Remove verified obsolete paths after consumer verification, respecting approved compatibility.

### Degradation
Protect existing approved invariants and security; add regression tests for changed behavior and independently derive high-risk tests. Prefer simplest correct maintainable change. No bypassing authorization, tenant isolation, transaction/idempotency controls, tests, types, lint or security. No hardcoded credentials, hidden fallbacks or silent failure. Check dependency necessity, provenance, license, maintenance and compatibility. Keep performance/observability and data lifecycle/recovery requirements proportional to real risk, with approved measurable budgets. Gate relevant build, lint, types, tests, security, secrets and dependency findings. Never use arbitrary global coverage percentage as sole criterion. Use native and existing tests first.

### Desynchronization
Before changing canonical contracts identify producers, all consumers, deployed compatibility needs, generated artifacts, migration/deployment order, tests and rollback. Update all current callers directly and docs in same task; regenerate where required; no manually maintained parallel schemas when reliable generation exists. Compatibility layers only for genuine documented need with owner and removal plan. Verify schema/event/API/client compatibility, generated freshness, translations and integration across workspaces. Coordinate writes in existing checkout, no overlapping scopes or Git/worktrees. Refresh relevant code and fingerprints before integration, report operator deployment/re-release requirements.

## 4. Blocking versus review decisions
Block when proven and applicable: required build/type/test failures under approved gate; unauthorized dependency cycles/boundary violations; newly introduced confirmed critical vulnerabilities or exposed credentials; unauthorized breaking public contracts; stale required generated artifacts; violated approved business invariants; other explicitly approved deterministic rules. Do not silently downgrade existing stricter project controls.
Review rather than blindly block/delete: semantic clone candidates, suspected dead code, increased complexity, new package/dependency, performance change without reliable comparable measurement, undocumented intent, architecture alternatives. A tool finding requires interpretation; absence of tool findings is not proof of correctness. Escalate high-risk uncertainty. Track confirmed historical debt without turning unapproved findings into TODO items. Use operator approval for exceptions; no unauthorized suppressions.

## 5. Verification and completion
For each approved task, use existing end-of-task checklist and additionally demonstrate all applicable items:
- Approved requirements and invariants satisfied; intended behavior and deliberate differences preserved; all affected consumers verified.
- Reuse and simplicity evaluated; canonical ownership and module boundaries respected; obsolete references removed except approved real compatibility.
- Required unit, integration, E2E, contract, negative/security, concurrency and regression checks passed, or explicitly state unrun/blocked checks. No changed expected assertions just to pass. Required independent cross-model review for critical security, auth, money, tenancy, inventory and data integrity before approval and after the fix, per SKILL.md. At least one validated different-family reviewer per stage; unresolved material disagreement or no eligible reviewer blocks closure.
- Performance, migration, recovery, data lifecycle and observability evaluated where relevant. Rollback and deployment/re-release requirements documented. No services/Git/env actions taken without required authority.
- Relevant project docs, generated artifacts, MEMORY.md, CHANGELOG.md and approved TODO handling complete per existing rules. A pure read-only review does not trigger unrelated docs updates; authorized report creation follows applicable documentation rules.
- Actual verification command, tool/version, scope, source anchor and evidence recorded. Compare to baseline and refresh invalidated coverage. Unresolved risks/approved exceptions remain visible; no false success.

Phase 4 final review: coverage matrix must include all active units, shared packages and relevant integrations across all four Ds; justified exclusions and unavailable checks must be explicit. Re-run comparable baseline checks and verify local/CI safeguards with safe fixtures. Report verified improvements and limitations separately. Do not claim COMPLETE if required coverage or approved work remains blocked.

## 6. Continuous prevention without a new bureaucracy
Per task: graph-first discovery, reuse/ownership check, impact analysis and existing completion checklist. Per applicable review/merge/release: approved deterministic checks, critical workflow/contract checks and recovery readiness. Periodic security/dependency scans and incremental semantic/architecture reviews based on risk, available infrastructure and operator-approved cadence; no automatic full rewrites. Re-audit changed domains and dependencies when anchors change. Do not create scheduled jobs or services without authorization. Keep one skill source, reuse project documentation, one approved task tracker per existing convention, and only essential baseline/audit evidence. Update policies only when real verified gaps justify it. Record confirmed lessons in existing memory/decisions; archive evidence per project policy. No duplicated policy trees.
