# 4D Engineering — Shared Execution Playbook

## 1. Purpose and scope
This is a remediation and prevention skill, not a replacement for engineering governance. Its primary purpose is to comprehensively audit and physically correct confirmed 4D problems throughout the entire existing active codebase of each product. Actual source modifications, removal of verified obsolete/duplicated implementations, consolidation of justified shared functionality, architectural corrections, security/quality fixes and synchronized contracts are expected outcomes. Every confirmed finding must have an explicit disposition; approved remediation must be implemented and independently verified as required. Reports, rule edits and gates alone never constitute remediation completion. Permanent prevention is the secondary objective. Unresolved or unapproved defects remain visible and are not reported as fixed. The four Ds are working categories, not an industry standard or proof that defects exist:
- Drift: deviation from approved architecture, ownership, patterns or constraints.
- Duplication: unnecessary exact, structural or semantic repetition, competing authoritative implementations and obsolete paths.
- Degradation: regressions, security and integrity weaknesses, unnecessary complexity, reliability and maintainability deterioration.
- Desynchronization: incompatible contracts, schemas, generated clients, configuration, documentation, consumers and concurrent agent changes.

A pilot validates the method; it does not satisfy full coverage. Review in critical domain slices across all active modules and connected code; perform workspace-wide and cross-workspace investigations when ownership or contracts cross boundaries. The objective is verified correct behavior, not maximum deletions, uniformity, minimum file counts, zero duplication or a perfect tool score. No assumption that AI-written code is defective, existing code is correct, or similar code is equivalent.

Use [AUDIT_AND_REMEDIATION.md](AUDIT_AND_REMEDIATION.md) for technical investigations and report templates, and [PREVENTION.md](PREVENTION.md) for gates and permanent protections. Load relevant sections on demand; use specialist review lenses, not a fixed number of agents. Keep this methodology in one canonical, content-hashed shared skill; product-specific facts and results belong in product documentation.

## 2. Authority, environment and hard boundaries
- Read the actual current global, workspace and affected module instructions, MEMORY.md, relevant skills, README, architecture, contracts and documentation in their required order. Read tool-specific instructions as well. Verify applicability and precedence; this skill cannot override any HARD RULE. If a conflict has no explicit precedence, stop the affected action and ask the operator. Continue only independent, authorized work. Do not rewrite existing governance to make the skill easier to execute.
- Zero Git operations by agents, including read-only commands, status, diff, log, rev-parse, fetch, branches, worktrees, PR creation, automatic isolation modes and indirect Git calls by scripts/tools. Do not access Git history or use a proxy to bypass this rule. Inspect commands and subprocess behavior before execution; where Git is required, describe the operator-owned step; provide Git commands only if explicitly requested. This stricter zero-Git prohibition applies to Nextkt despite its less restrictive local Git wording. Never use `codex review`, `--worktree` or OpenCode worktree modes. Do not use Git-derived changed-file gates unless operator supplies an authorized file manifest or an existing operator-authorized CI mechanism can supply scope without agent Git operations. Never change Git-deny settings.
- Never start, stop, restart or kill services, containers, watchers or development servers. Use static analysis, safe isolated tests and already-running authorized services only as allowed by the project. Inspect test/build scripts for prohibited side effects. A required unavailable service is a blocker; give the operator the exact command. Do not execute production migrations, load tests, financial actions or external API mutations.
- Do not edit, create, copy values between, or synchronize .env files without explicit authorization. Global env synchronization and local env restrictions can conflict: resolve with the operator before implementing a dependent change; do not silently declare local or global precedence. No hardcoded secrets or fabricated env values. Observe project-specific database selection, Docker-only keys and public URL restrictions. Never print secrets; redact tool output and reports.
- Never overwrite unrelated changes. Use the current checkout only, not branches/worktrees. Do not install tools, add dependencies, change CI, send proprietary code to external tools, use production data, deploy or alter global agent settings without explicit scope approval. Do not use scanners that upload code unless authorized. No unapproved destructive actions.
- In Claude Code only, follow the current model split: Opus leads decisions and review and may read source directly; for auth, money, tenancy, inventory, data integrity and other critical findings Opus must personally verify source evidence. Haiku performs general discovery/reading; Sonnet performs all file writes (including reports) and test execution where required by Claude instructions. Targeted diagnostic and regression tests may run before a fix when justified; full applicable post-fix verification is mandatory. Avoid redundant tests. These operator-approved 4D exceptions do not remove other role restrictions. Verify the actual instructions and available models. If required models or permissions are missing, stop the affected work; do not substitute another model family. Do not bypass role rules through tool delegation. Other agents follow their native instructions, not Claude's model names. Engineering Policy prevails over Ponytail’s shortest-diff preference; never use a plugin that violates governing rules.
- Use codebase-memory-mcp before raw code search when available or mandatory. Confirm indexed projects, canonical real paths, freshness and relevant cross-module graphs. Treat symlink aliases as one physical unit; do not double count. Re-index stale/missing projects only when permitted and safe (including zero-Git compliance). Do not delete cache databases or alter MCP settings without approval. If unavailable, follow the project's authorized fallback; report reduced confidence or stop if no fallback is permitted. Do not claim graph results prove behavior; read actual definitions and call sites.

## 3. Agent allocation and execution safety
Use one coordinator per authorized workspace or cross-workspace scope. Audit lenses in AUDIT_AND_REMEDIATION.md are mandatory where applicable; no mandatory specialist headcount. Allocate subagents only for relevant expertise, parallel read-only investigations, context isolation or independent review, subject to actual model rules. The coordinator owns scope, decisions and report updates. Do not spawn worktree-based agents. Parallel reads are permitted; parallel writes only when file scopes and semantic dependencies are demonstrably independent. Serialize shared packages, schemas, contracts, configs, central documentation and overlapping files; use one writer for shared records. If another session or user changes a file, re-read it, re-evaluate dependencies and stop on unresolved conflict. Verify current source fingerprints before writing. Do not attempt to lock out the operator or overwrite unrelated edits. Separate reviewer from implementer for critical changes; if genuinely independent review is unavailable, record a blocker instead of claiming it occurred. Before each remediation batch, obtain operator confirmation of a recoverable restore point for every affected repository and record its reference and scope. No writes to product code until confirmed; a hash is not a restore point. Do not create backups or run Git without authorization. Prefer one implementation writer at a time.

### Independent cross-model review
For critical findings/fixes (auth, security, money, tenancy, inventory, data integrity and other high-impact architectural or contract changes), independently investigate before operator approval and independently verify after implementation. The lead retains responsibility for source evidence and final tests. Reuse the existing canonical `dirsal-llm-coding-council/scripts/native_council.py` engine with one round, no peer ranking, voting, HTML or full Council flow. No new orchestration system, no paid API fallback. Standard low-risk work uses native review; medium-risk work may use one approved independent reviewer; critical work requests both Codex and Gemini when validated. At least one different-family, eligible reviewer must actually complete each critical review stage; otherwise BLOCKED. Do not substitute the Claude seat when Claude leads. If a different lead is used, select reviewers from distinct families and record the actual eligibility; stop if the existing interface cannot safely support this.

Live source review is the preferred mode for independent discovery; evidence-only excerpts are useful for bounded questions but cannot establish full independent codebase coverage. Before any live invocation, the operator must approve disclosure of the bounded scope to each provider and the locally validated controls: read-only filesystem, permitted read-only MCP, safe startup hooks, scope/secret isolation, no Git even read-only, no services, no recursion and no network/tool actions outside approved scope. `--live-verified` is an operator-confirmed assertion, not a sandbox guarantee. Read-only mode cannot by itself prevent read-only Git or secret reads; enforce with verified tool restrictions or isolated approved source exposure. A failed safety check blocks that reviewer; do not widen permissions. Do not send secrets, env/key files, production data or unapproved code. A canary is evidence of a specific control, not proof of universal safety.

Example interface (replace placeholders with verified absolute paths and approved non-secret brief; do not execute until authorized). Use `--seats codex` alone while Antigravity is NOT_RUN. Explicit model IDs are requests, not attestations; verify current accepted mapping in Phase 1. The engine requires `--approved-context` and a question or question file, in addition to live and workspace flags. Use one canonical workspace per invocation; separate authorized roots for cross-product review. In Kisum present operator commands with absolute `cd` and `&&` as required.

```bash
python3 "$HOME/.agents/LLM-Skills/skills/dirsal-llm-coding-council/scripts/native_council.py" --rounds 1 --seats codex antigravity --live-verified --workspace "/verified/absolute/workspace" --approved-context --codex-model gpt-5.6-sol --antigravity-model gemini-4-neon-high --timeout 300 --question-file "/approved/non-secret/review-brief.md"
```

Prepare the approved brief in an authorized temporary/record location outside the fingerprinted workspace (or pass a non-secret question using the verified CLI interface); no unapproved persistent files. Include the stage (pre-fix discovery or post-fix verification), scope, applicable canonical rules and invariant references, approved file/contract boundaries, forbidden operations and the finding format in AUDIT_AND_REMEDIATION.md. Give reviewers the question and scope, not the lead's findings or conclusion; let them trace the code themselves. For post-fix verification give approved expected behavior and change scope, not an asserted pass. Never let a reviewer call another agent, Council or executable skill; no write-capable tools. Reading binding instructions is required. If the engine's free-text response cannot satisfy the required finding format, record malformed/unverified, not PASS.

Record a deterministic full in-scope workspace fingerprint before and after every review invocation (including all affected repositories and tracked audit targets, not merely `--evidence` files). Use the non-Git method in AUDIT_AND_REMEDIATION.md; record exclusions and verify file path additions/deletions/renames as well as content. Excluded secrets, caches and external paths require independent preventive controls; do not hash secrets. Pause implementation writers during review. Any unexpected change voids the affected review and stops affected work; preserve operator changes and investigate without reverting automatically. Fingerprints detect changes, not attribution or all possible writes. No live review if safe controls or complete in-scope fingerprint coverage are unavailable. A simultaneous round is bracketed by one before/after fingerprint; if changed, void every response in that round.

Record reviewer family, requested model, effective model only if independently confirmed, scope/fingerprint, stage, evidence, verdict and limitations. A timeout, missing reviewer, malformed answer, quota/auth failure or failed safety check is NOT_RUN (with reason), never agreement. One controlled retry only if authorized and safe; no retries for unsafe configuration or unauthorized scope. Resolve disagreements by lead re-reading cited code, approved requirements and reproducible tests; no majority voting. Unresolved material disagreement is BLOCKED. The engine's `status: complete` describes orchestration only; it is not a finding or remediation verdict. Do not mark a critical item verified without the required eligible independent review and applicable checks.

## 4. Four phases (explicit approval boundaries)
### Phase 1 — Baseline & Pilot
Read rules and discover the whole workspace: all repositories, modules, active/legacy status, languages, ownership, integrations, deployment surfaces, existing tools and scripts, test coverage, known risks and authoritative docs. Discover linked products only within authorized read scope; record inaccessible boundaries. Build a compact coverage inventory and select a critical domain with its connected dependencies (auth, tenancy, money, inventory or other product-critical path). Record verified non-Git baseline using AUDIT_AND_REMEDIATION.md; use native tools first. Report unavailable metrics, no guesses. Run a read-only pilot using all four lenses. An explicitly authorized report-writing audit may write designated reports only, plus documentation required by governing rules; pure review with no file changes must not touch project docs. Keep production code/config unchanged. Before live reviews, perform a bounded Phase 1 validation: inspect actual engine arguments and installed CLI/model mapping; verify canonical rules and companion files load in each agent, including workspace-level rules, without duplicate discovery; verify code graph and allowed read-only MCP (configure Antigravity only after separate approval); inspect hooks and tool restrictions for Git, writes, service execution, secrets, recursion and scope escape. Use an operator-approved disposable synthetic workspace with no secrets, harmless read and blocked write canaries, and negative checks for prohibited tool access; compare fingerprints, verify effective protections and record exact results. Never attempt destructive commands or Git to test denial; use policy inspection and safe stand-ins. Antigravity plan/sandbox remains NOT_RUN for live review until its restrictions are verified. Codex may serve as the sole independent reviewer only if its own safety and scope checks pass. If no reviewer is eligible, block critical remediation, but continue safe authorized discovery and low-risk work. Validate structured finding responses and independent real-code discovery on the approved pilot, with provider disclosure approval. A successful probe or evidence-only Council round does not qualify live access. Present pilot evidence, coverage, limitations and proposed initial gates. Stop for approval of gates and any remediation; urgent risks are reported immediately, not silently fixed.

### Phase 2 — Early Protection
Before broad remediation, reconcile approved global 4D instruction changes (see PREVENTION.md) and implement only approved initial local deterministic checks and, if separately approved, CI enforcement as described in PREVENTION.md. Prefer existing commands, native checks and minimal additional tooling. Measure full applicable scope against baseline, not just modified files. Block new confirmed objective violations without hiding existing critical risk; do not establish unverified architecture rules or business requirements as gates. Keep existing checks at least as strict as they were. Test both passing and deliberately failing safe fixtures. Record exact commands, results, enforcement and operator actions. If no CI exists, local checks are useful but not CI enforcement. Do not claim an automated gate is active without evidence. Request approval before starting code remediation.

### Phase 3 — Iterative 4D Audit & Remediation
Prioritize critical security, money, tenancy, inventory, data integrity and core workflows; then remaining domains, shared packages and support/infra. Sequence by dependency and risk, not by D or folder count. For each slice:
1. Refresh source anchors and graph discovery; trace owning modules and all relevant consumers, including other workspaces and deployed contracts. Review all four lenses using AUDIT_AND_REMEDIATION.md. Search broader than the slice when semantics, contracts or shared capabilities are involved.
2. Document findings and coverage in the audit report; classify confirmed/suspected/intentional/false positive/blocked. Consolidate findings by root cause, with one primary owner and linked secondary lenses. Report only actionable evidence, not bulk unvalidated scanner output.
3. Obtain the required pre-fix independent review of critical findings and resolve material disagreements. Present confirmed remediation candidates and explicit acceptance criteria for approval. Only agreed open tasks enter existing TODO structures. Do not treat audit permission as blanket write permission. Approval can cover a bounded batch of task IDs; do not require repeated approval for every safe edit within that scope. New scope, behavior, architecture, dependencies, public contracts, security policy, environment or destructive changes require the relevant explicit approval.
4. Apply Evidence Before Modification from AUDIT_AND_REMEDIATION.md. Confirm and record operator restore points for every affected repository before writing. Establish baseline behavior and run technically justified targeted diagnostic/regression tests before changing it; do not run pointless or redundant full suites. Implement a coherent minimal correct change across all affected callers, remove verified obsolete paths, preserve intentional differences and required compatibility. Update affected documentation, memory, changelog, generated artifacts and existing TODO items according to actual rules. No temporary shims simply to shrink a diff. A slice is not a boundary for fixing a proven cross-module root cause.
5. Run targeted checks and applicable workspace-wide checks; obtain the required post-fix independent review of critical changes and reconcile differences with actual evidence. Record before/after evidence, remaining risk, operator-owned actions and rollback requirements. Re-open coverage if affected code changes invalidate it. Repeat until all active inventory and relevant connections have a justified disposition. Do not let a large finding list stall safe, approved fixes; do not let a successful pilot end the program.

Perform an explicit cross-workspace contract/ownership pass in Phase 3. Review both producer and consumer sides where access is authorized. For unavailable external consumers, use approved contract evidence and mark unverified behavior; do not claim full integration coverage. Cross-workspace write scope requires explicit authorization for each affected product.

### Phase 4 — Permanent Prevention & Verification
Use PREVENTION.md to extend only missing rules and verified gates. Validate all applicable audit coverage, rerun comparable baseline checks, confirm real consumers and business invariants, remove approved obsolete references, verify gates with safe fixtures and report remaining exceptions/blocked items. Use existing project documentation and tracking; no parallel governance tree. Obtain independent risk-based review of final coverage and unresolved critical risks using validated reviewers; do not claim it ran when unavailable. Record an explicit conclusion: COMPLETE only when coverage and approved fixes are verified and no required action remains; otherwise PARTIAL/BLOCKED with named residual risks or approved exclusions. Record the conclusion for later sessions. Continue preventive checks on tasks, reviews and releases, with periodic incremental reviews proportional to risk and actual infrastructure; no autonomous recurring work or scheduled infrastructure changes without authorization.

## 5. Persistent state without bureaucracy
Reuse existing documentation/tracker conventions. Choose the existing appropriate engineering documentation location; if none exists, propose docs/engineering/4d/ at the workspace root (not within each module). Only create BASELINE.md and AUDIT_REPORT.md when approved and when equivalent records do not already exist. Use the exact templates in AUDIT_AND_REMEDIATION.md; no empty speculative files at skill installation. Existing product docs/MEMORY.md remain authoritative for intended business behavior and decisions; create BUSINESS_INVARIANTS.md only if no appropriate existing source exists and after approval. Do not duplicate business rules; record invariant references and tests in audit evidence. Existing ADRs if used hold architectural decisions, otherwise use established MEMORY.md conventions. Existing CHANGELOG.md holds meaningful implemented changes. Existing TODO holds only open agreed tasks, not findings, history or new completed entries. Nextkt uses its current versioned TODO/ convention, not a root TODO.md; discover next version from actual files. Respect each product's completed-task handling. Record only a concise active-focus pointer in MEMORY.md when applicable and authorized by documentation rules; do not duplicate the report.

On explicit program resume: read current rules, required memory, baseline and top coverage matrix of audit report, then applicable approved TODO entries and relevant findings. Reconcile non-Git fingerprints and scope, refresh invalidated coverage and select the next approved unblocked slice. Do not search old conversations, Git history or unrelated sessions. Do not infer approvals from old work or rerun completed work unnecessarily. Unrun checks are NOT_RUN; unverified findings are not facts.

## 6. Operator interface
Support explicit requests: review-only (no writes); start phase 1 for a named workspace; apply approved phase 2 gates; audit next domain in phase 3; remediate approved IDs; resume the named 4D program; phase 4 verification; periodic read-only review. If the request only asks for assessment, do not initialize files or perform remediation. Report in the operator's required language/style. State verified changes, evidence, limitations, pending approvals and exact operator actions. For affected releases, state redeploy order, mobile builds, migrations, env/secret changes and rollout compatibility according to existing rules. No task is complete until required docs, checks and independent review are done.
